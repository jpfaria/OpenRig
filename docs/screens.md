# Telas principais

Pedalboard virtual: usuário monta cadeia de efeitos visualmente, ajusta parâmetros em tempo real, toca com áudio profissional.

- **Launcher** — criar/abrir projetos. The running version sits bottom-right; on macOS, when GitHub's latest release is newer, a blue **Update to vX.Y.Z** button appears next to it and opens Terminal running `curl -fsSL https://raw.githubusercontent.com/jpfaria/OpenRig/develop/scripts/install-macos.sh | bash`. The check runs once per launch on a background thread; offline or rate-limited = no button.
- **Setup wizard** — opens over everything on first launch, while no audio device is saved yet. It walks the Settings sections in order: Language → Audio interface → I/O bindings → TONE3000 key. The left rail shows the steps (done ones carry a check), the content is the same section Settings shows, and the footer has back (absent on the first step), **Skip** (only on TONE3000, the optional step) and next (a check on the last step, which closes the wizard). Entering the Audio step enumerates the audio interfaces, rows already saved in the system `config.yaml` come checked; next on Audio saves the devices and moves on only when at least one input and one output are chosen. Without a project open, the I/O bindings made in the wizard are written to the system `config.yaml` when the user leaves that step.
- **Project Setup** — pede o nome ao criar novo projeto
- **Chains** — the block chain view, with drag to reorder. Tapping a chain row's header selects it (outlined) as the active chain — the one a MIDI footswitch bound to `toggle_active_chain_enabled` acts on. A block whose model is not installed (an uninstalled NAM/IR/LV2 pack, or one unsupported on this platform) loads **disabled** and is shown dimmed with an amber tint, distinct from a manually-switched-off block; the chain keeps playing without it and its enable toggle stays inert until the pack is installed and the catalog reloads. On desktop each chain row draws its chain as a graph: an input node, the shared blocks and, for each split, its N lanes (A, B, C, … top to bottom), joined by a mixer node (Split → Mix) or each ending in the output node of its Y leaf (Split → Y), then the output node. A split may sit inside a lane, at any depth; the app lays the tree out by itself (no stored position) and the row grows to the height and width the laid-out graph needs, while a linear chain keeps its old height. Block cards keep the strip chip's icon, LED, unavailable tint, MIDI markers and hover tooltip; the wheel keeps scrolling the list and Cmd/Ctrl + wheel zooms the row. The input and output nodes read a fixed **IN** / **OUT** in a small box, never the endpoint names. Click a card to open its editor, a split or mixer node for the knobs of that split, an input or output node for its endpoint checklist. "+" on a wire, or at the end of a lane, adds a block at exactly that place, at any depth. Drag a card within its lane, to another lane or depth, or between shared and lane positions; dragging a split node or its mixer carries the whole split (its lanes and everything nested in them) to another "+", never into its own lanes; a drop the chain cannot take snaps back. Removing a split node (its × on hover) removes that split only, and asks first when any lane but A holds blocks — lane A's blocks take the split's place, the other lanes' are deleted. Touch mode keeps the pedal strip, where each split is a single Split chip that opens the editor on that split. Every "+" picker is a grid of large icon tiles (the icon above the type name, a strip in the category colour on top) and offers every block type plus **SPLIT MIX** and **SPLIT Y**; the only refusals are the split rules: no split behind a Y in the same list, **SPLIT Y** only where no block follows in that list (at the top level the chain's own ports may), and a picker opened inside a lane lists no Input, Output or Insert (Select and both splits are allowed). The split node opens a small panel with the Mix / Y switch, the **paths row** — one chip per path, an × on each chip while the split has more than two paths (removing a path that holds blocks asks first), and **+ Path** — then mode, the level into each path and the balances; the mixer node opens level, pan and polarity per path, master and master sum. An input or output node opens its endpoint checklist (every physical endpoint of the chain's E/S once, named by device and channels like "Quantum HD 8 · Out 1/2", checked by default); every Y leaf has its own output node.
  - **Per-stream meters** — the chain card footer renders one INPUT/OUTPUT peak-meter row per live input stream the chain runs. **Each row is named after the audio interface, never the I/O binding:** the left label is the interface the stream reads from (the chain's head input, or an insert's return on the return segment), the right label the interface its output writes to, as the host names it (`Quantum HD 8`). The names come from the device list the app already enumerated (`infra_cpal::cached_device_descriptors`, read by the GUI through `device_refresh_list::cached_devices`; never a new enumeration from the meter timer); until the first enumeration lands, or for an interface the host no longer lists, the row shows only its direction and channels. The rows and their endpoints come from the same segment map that counts them (`engine::stream_io_labels`). **Each meter also shows its direction and channels** — the interface name is followed by a blue `IN 1` on the left meter and a violet `OUT 17,18` on the right one (1-based interface channels; several outputs joined with `+`). Two guitars into the same cab show the same `OUT` channels. An input that feeds several outputs is listed **once** on the left — inputs on the left, every output on its own row on the right, never the same input twice. A meter the project cannot name shows just `IN` / `OUT`. The compact view's footer rows show the same. **The rows are behind a meters icon** in the chain card header, beside the looper and the DI fone, and behind the **METERS** section of the compact view's accordion: the icon and the section show only while the chain is **enabled**, and the rows start **hidden** — a click shows them, another hides them. On the card the flag lives in the row model (`ProjectChainItem.meters_expanded`), so it survives the row rebuild every edit triggers while the same chain stays in that place; it is never saved, and the compact view starts hidden each time it opens. The rows are a **live surface**: they only appear while the chain is **enabled**. A disabled chain (including every chain on a freshly opened project) shows **no** meter rows. When enabled, the row count follows the chain's **streams** — one per `(input × output)` pipeline, so a chain with a mid `Input` and a mid `Output` shows four rows and every port has its own clip indication — and the meter timer fills the live dB values.
  - **Project tempo** — the project has one tempo, like a band. The top bar shows it once, left of the back arrow: **−** / **+** nudge it by 1 BPM and **TAP** taps it (`ProjectTempo`, `adapter-gui/ui/components/project_tempo.slint`; the same `SetMetronomeBpm` / `MetronomeTap` commands as the metronome window, so they never disagree). The tempo is saved in `project.yaml` (`bpm`; a project without it opens at 120 BPM). The metronome, the drums and every synced delay and modulation follow it (see `docs/blocks-catalog.md` → "Tempo sync"). Chains and presets carry no tempo of their own.
  - **Preset bank dropdown** — the per-chain preset selector opens a search-as-you-type finder: a search field filters the bank by name, and the list scrolls inside a height-capped popup so a large bank never runs past the screen (mirrors the block model picker). Each row keeps its original bank slot, so selecting a filtered entry switches to the right preset. The same dropdown is used in the Compact Chain View.
  - **Virtual DI loop** — each chain tile has a DI-loop icon button next to the per-chain volume knob. Clicking it expands a control row with: (1) a **select / dropdown** to choose the DI source, and (2) a **play / stop** toggle button. Available sources are the bundled CC0 dry-DI loops (shipped under `assets/di-loops/`) then every **saved looper take** from the app-wide take library (listed by file name, e.g. `verse.wav` — a take saved on any chain or in any project shows up here, and a take added or deleted by hand in the folder is picked up too), plus a **"Choose file…"** entry that opens a file picker for a user-supplied WAV. Picking a take is simply a `DiLoopSource::File` pointing into the library, so it plays through exactly the same isolated DI stream as a hand-picked file. Pressing play replaces that chain's live device input with the looping DI buffer — the full block graph (amp, cab, pedals) processes it exactly as it would process the guitar signal. All other chains keep their real hardware input unaffected (per-stream isolation). The DI file must be a **dry DI** (clean guitar, no amp or effects); feeding already-processed audio will double-process the tone. A mono DI is broadcast to stereo (`Stereo([s, s])`); a stereo DI is used directly. If the chain has **several input sources**, the loop plays once — through the first source — and the other sources stay muted while it runs, so playback is never doubled. The loop is **resampled to each output stream's own device rate** when it is armed, so on a multi-rate rig (e.g. a 44.1 kHz interface and a 48 kHz interface at once) every output plays at correct speed/pitch — not just the one matching a single global rate. Changing the device rate while a loop is playing re-arms it at the new rate, so it never drags into slow motion. The loop choice and on/off state are **ephemeral (runtime-only)**: they are never written to the project (`project.yaml`) — consistent with ADR 0003. Reopening or reloading the project returns every chain to its live hardware input. **Isolated streamed DI:** the DI loop never touches the guitar's stream. Arming builds a fresh routed copy of the chain's block graph on a worker thread and **streams** the loop through it into a lock-free ring the chosen output's callback drains — playback starts within milliseconds regardless of loop length, the worker only produces what the output consumed (ring backpressure → the output clock IS the DI clock, no drift), and no DSP runs in the callback. The sound is mixed into the **chosen output only**; the guitar's live signal, meters, and other outputs are untouched (invariant #4). The DI runtime is a snapshot of the chain: block edits made while the loop plays apply on the **next** play. The DI panel has a second select listing **every physical output of the project** — the same list the backing-track player, the metronome and the looper offer, by device and 1-based channels ("Quantum HD 8 · Out 1/2"), outputs outside the chain included; picking one dispatches `SetChainDiLoopOutput` and a playing loop re-renders onto the new output, played on that output's own device channels (on JACK an output outside the chain falls back to the chain's main output). The choice persists per-chain in `project.yaml` (`Chain.di_output`, ADR 0003; absent → the chain's main output). The **DI meter row** (compact window) shows the DI stream's **own** in/out levels, read from the playback's peaks — not a mirror of the chain meters.
  - **Looper** — each chain tile has a loop icon next to the DI fone. Clicking it opens the **looper panel** at the window root (an inline panel, never a `PopupWindow`, so every control is reachable: a `PopupWindow`'s rows do not receive clicks in this app): one **stacked row per looper**, plus a **+ Add** button, and an empty state explaining what a looper does. A chain can hold up to **8** loopers and they are fully independent — any number can record or play at the same time. Each looper is **single-take** (one recording, no overdub layers): to stack parts you add another looper, not layers on one. REC starts the recording and a second REC closes it; there is no undo/redo. Once a loop has material its **REC is disabled** — clear it to record again. **Loop sync:** the first loop recorded on a chain is the **master**; every loop recorded after it **quantizes its length to a whole multiple of the master** and, on close, **all the chain's playing loops restart from the top together**, so the stack plays locked to the same bar. **REC needs the chain running** (it captures the live input), but **PLAY only needs the output** — a recorded loop keeps playing (and can be stopped/replayed) even with the chain turned off, on its own isolated output stream. Each row carries a 40 px transport (record · play/stop · clear), the state as **colour AND label** (grey empty, red recording, blue playing, light grey stopped), a position bar with `0:03 / 0:08` at the stream's real rate, a gear that opens the row's **parameter drawer** (record-from **input** and play-to **output** selects — a field showing the current endpoint that opens a root-level list, never a row of buttons — level, decay, speed ½×/1×/2×, reverse), and an × that removes the looper. Each looper picks **which input it records from** (so on a multi-input rig REC captures the input you actually play, not always the first) and **which output it plays to** — any physical output of the project, from the same list the DI, the player and the metronome offer. A looper records the chosen input's **dry signal**; playback runs on its own **isolated stream** — a routed copy of the chain into the chosen output (the same isolated pipeline as the DI loop), so input and output are fully independent and the loop never mixes into the record chain (invariant #4). **Tone independence (phase 2):** because the loop records **dry**, it carries a reference to **which preset renders it** — so you can record on preset A, switch the chain to B to solo live, and the loop keeps A's tone. On a **fresh** RECORD the loop is linked to the chain's currently-active preset; the drawer's **preset picker** (a `Preset ▸ <name>` button that opens a root-level modal listing the chain's bank, plus a *follow the chain* entry that clears the link) reassigns it at any time. Editing the linked preset's blocks re-renders the loop through the new tone on the next play. The playback stream is built from the **linked** preset's effects — a routed copy of the chain with its processing swapped, same I/O and stream identity so isolation is untouched (invariant #4). The link is a `Command` (`SetChainLooperPreset`) so MCP/gRPC reach it too, and it persists on the chain (`LooperConfig.preset`; rig projects store it inside the `RigInput`'s loopers). **REC is offered only while the chain is running (enabled)** — recording captures the live input through the chain's runtime, which exists only then, so on a stopped chain the REC button is disabled (dimmed) rather than a dead press. Play/clear act on already-recorded material and stay available regardless. **A loop's state (the recorded audio and its transport) lives in the controller, not inside the chain's audio runtime** — so stop/clear/remove take effect immediately and a loop survives an enable toggle or a project reopen instead of being lost when the runtime rebuilds. Level and reverse shape the playback; speed is a follow-up. Recording is capped at **60 s**. Loops are per chain and per runtime: nothing is shared with another chain (invariant #4). A **footswitch** drives the first looper of the active chain through the MIDI slots `looper_record`, `looper_play_stop` and `looper_clear` (see `docs/midi-profiles.md`). **Waveform editing:** a recorded loop can be reshaped. The row's **pencil** opens the **waveform editor** — a root-level overlay (never a `PopupWindow`) showing the take's peak envelope with two draggable handles, its length in the header, and **Fit**, **Trim** (move the loop bounds inward), **Crop** (keep the selection), **Cut** (remove the selection and close the gap), a **play/stop** so the result is judged by ear without leaving the overlay, plus **Undo** / **Redo** for the edits themselves. **Fit** is the no-selection button, and it listens to the take: a loop base is a riff or progression played over and over, so Fit measures how long one pass of that pattern is (from the audio alone — the loudness of the playing in frequency bands and its harmony, compared with itself shifted in time) and keeps **whole passes from the first attack**: the count-in goes, and so does an unfinished pass at the end, so the loop's end runs into its start. A last pass that is only missing its final ring-out still counts. When the playing does not repeat clearly enough to tell, Fit falls back to where the playing actually starts and ends (a run above the noise floor, with a margin so no attack is clipped) and trims the silence off both ends. The analysis runs on the control thread, never the audio thread. Editing is **stopped-only** — the button is dead while the loop records or plays, because a live take must never be reshaped under the player's feet — and the edit **consumes the take**: the result is a single layer, exactly like a loop restored from disk. Every seam is blended with the same equal-gain overlap-add the DI loop uses, so a cut joins and the loop wraps without a click; a cut therefore costs two seams and a trim one. **An edit keeps the loops together:** every loop of the project sits on one shared timeline, so an edit is carried to every other loop that lines up with the edited one — a loop a whole number of times as long loses the same region from each of its cycles, and a shorter loop that divides it is first repeated up to its length, the way it plays under it — so they all stay a whole number of the new cycle and restart together. Every loop the edit touched lands stopped. A loop whose length neither divides nor is divided by the edited one's, and a take still being recorded, are left alone. One **Undo** or **Redo**, pressed on any of the loops an edit touched, steps all of them. Edits are their own **undo stack** (capped at 8, cleared when the loop is cleared or re-recorded) and are independent of the transport's undo, which is a no-op for the single-take looper. The edits are `Command`s (`EditChainLooperAudio` / `UndoChainLooperEdit` / `RedoChainLooperEdit`), so MCP and gRPC reshape a loop through the same path the GUI does, and the selection's meaning (clamped to the loop, ordered, resolved to frames) lives in the core rather than in any frontend. The edited loop is written to disk on the next project save. Recorded audio is saved with the project as a wav under `<project>.loops/` and comes back **stopped** (never auto-playing) when the project is reopened, resampled if the interface now runs at a different rate; the parameters travel inside the `project.yaml`. **Saved takes:** each looper row has a **floppy** beside its transport — enabled once the loop has material and is not recording (a playing loop can be saved). It opens a **Save take** dialog (a root-level modal, never a `PopupWindow`) with a name field, **Save** (dead while the name is blank) and **Cancel** (**Close** once saved). Save keeps the loop's mixdown (the same PCM the project save writes, via `export_chain_looper`) as `<name>.wav` in the **app-wide take library**, `looper-takes/` under the user folder (`~/.openrig/looper-takes/` on macOS and Linux, `%APPDATA%\OpenRig\looper-takes\` on Windows) — not beside the project, so **every project** sees it. The name is made disk-safe (anything that could leave the folder becomes `-`); an existing take is **never overwritten** (the save is refused and the typed name kept so it can be changed), and a looper with nothing recorded (or a stopped rig) has nothing to save. The dialog says which of those happened. Saving is `SaveChainLooperTake` on the command bus, so MCP saves the same way; `openrig://paths` reports the folder as `looper_takes_path`. The write happens on the control thread, never the audio thread. **Deleting a take:** in the DI panel's source list every saved take carries a **trash** at the end of its row (the bundled DI loops and "Choose file…" never do — they are not the user's). The first click only **arms** it: the button widens to a red **Delete?**; a second click on it deletes the take's file from the library. Clicking anywhere else in the list, or closing it, disarms it, so a stray click never loses a take. The row leaves the open list at once; if the take was selected the selection clears. Any chain whose DI is playing or holding that take stops and unloads it. Only a plain file name inside the library can be deleted — nothing outside the folder is ever reachable. Deleting is `DeleteLooperTake` on the command bus (`delete_looper_take` in MCP); a refusal shows in the status toast.
- **Block Editor** — edita parâmetros de um bloco. The header's model select/search picker is shown only for catalog-backed block types; the generic NAM (`nam`) and IR (`ir`) file-loader blocks have no catalog model to choose, so their header shows the loaded model name as a static label instead of the picker. The editor window sizes itself to its content so every parameter is visible without scrolling — the panel (knob-grid) editor grows vertically as knobs wrap into rows, and the form editor grows with its parameter count. **Adding a block opens the same editor:** outside the inline fullscreen/touch mode, picking a block type opens this very editor in **add-mode**, so the parameter tabs are there while you are still choosing the model, exactly as when editing an existing block. The two modes differ only in commitment: in add-mode the confirm button reads *add*, the delete affordance is hidden (there is nothing to delete yet), and **nothing is written until you confirm** (no auto-persist as you turn a knob, no live stream refresh), so abandoning the window leaves the chain untouched; editing an existing block persists each change. **A group of one knob is not a tab:** the tab bar is built when the grouping actually divides the block — the one-knob groups outnumbered by the real ones, as in a NAM package's `Capture` axis (some ship a single one) beside its `Amp` / `Noise Gate` / `EQ` modules — and not when it does not: a native amp's ten knobs spread over seven groups, five of them a single knob, are its one front panel, and so are a saturation's four one-knob groups. Above one panel (twelve parameters, two wrapped rows) the bar is built regardless, since a tab beats a knob the window cannot show. The schema keeps grouping the parameters either way — the grouping orders them and the compact strip reads it. The rule lives in one place, so the editor window and the compact row can never disagree about whether a block has tabs. In the compact view a parameter's knob is centred under its label. **A model with a curated knob layout and more than one parameter group renders the tab-filtered grid instead of its curated knobs:** the curated overlays are drawn in layout order and know nothing about the tab bar, so they would draw the same knobs on every tab and leave the parameters the layout omits (`input`, `bright`, `output`) without a control. A model whose parameters form a single group (`gain/volume`) keeps its curated knobs, tab bar and all. **Blocks drawn by an EQ widget have no parameter tabs:** the CurveEditor (parametric EQs) and MultiSlider (graphic EQs) own the whole parameter surface and the knob grid the tabs filter is never shown, so a tab row would be inert and push the band sliders past the bottom of the window.
- **Compact Chain View** — single-chain focused editor: power switches, quick model swap, preset/scene picker, volume, configure I/O, and a **measure-latency** button whose result renders as a badge **inside this view** (next to the sonar button), not on the chains list behind it. Its block-type picker uses the same tiles as the Chains screen, so the icons match. Chain reorder (move up/down) is intentionally absent here — it lives only on the Chains list, which is the multi-chain view. **Rows size themselves to their parameters:** a block's parameter strip wraps into as many lines as it needs and the row grows to fit them, instead of clipping the params away at a fixed height; a block whose parameters carry 2+ groups (a VST3 plugin's manifest groups, or the dynamic grouping) gets a **tab bar** on top of its strip and shows one group at a time. A block with a single group and one line of knobs looks exactly as it did before. Which tab a block shows is view state — it is never written to the project — and it survives the model rebuild that every parameter edit triggers. The view follows the project whoever changed it: a parameter set over MCP or MIDI, or turned in the block's own editor window, while the compact view is open shows on its knobs immediately. The drag-to-reorder drop indicator follows the real row boundaries, since rows do not share a fixed height. **Accordion sections:** the header keeps only power, title/preset, volume, the latency probe and its badge, configure and delete. Below the block rows sit five sections, each behind a `SectionToggle` header like the mixer's — chevron, the icon its old header button had, title (`ui/components/compact_chain_sections.slint`): **MIXER**, **DI** (the DI loop panel), **LOOPER** (the chain's loopers, the same panel as the chain card's, with its waveform editor, Save take dialog and preset picker opening over this window), **TONE DOCTOR** and **METERS** (only while the chain is enabled). One section is open at a time: opening one closes the other, a second click closes it, and every section starts closed each time the view opens. Each section body is the panel itself, laid flat across the view (no box, border or title of its own — the section header names it), and a tall one scrolls inside the room the block rows leave. The looper section's actions reach the same looper callbacks as the chain card (`compact_looper_wiring.rs`), and its rows are the card's live loopers, mirrored by the view's poll. Nothing opens as a floating window any more. **Splits:** a chain with splits lists every block in signal order: each split row, then its paths in order (A, B, C, …), then the blocks after it; a split inside a path lists its own paths right after its row, and every row is indented by its depth (16 px per level). The split row shows its icon, its kind (SPLIT MIX / SPLIT Y) and the split's knobs (mode, the level into each path, balances), editable right there; a Mix split adds a **Mixer** tab with the mixer's knobs. It has no model selector, and opening it opens the split editor. Each path block carries its path's letter as a badge on its type icon, and every action on that row acts on that block: power, remove, parameters, model, open, "+" and drag. A drag reorders only within the list the block is in.
- **Settings** — unified configuration screen, reached from the top bar. Two scope headers:
  - *System* (persists to `config.yaml`, stays on the machine when you move the `project.yaml`):
    - **Audio interface** — input/output device, sample rate, buffer size, bit depth. Saving the devices with a project open also creates or updates the `default` I/O binding so new chains always have a binding to reference.
    - **I/O bindings** — list, create, edit, and delete named I/O bindings. **New binding** sits at the right end of the page title row. Each binding is a **collapsible accordion**: collapsed by default showing only its name plus In (green) / Out (orange) endpoint counts, so a list of several E/S stays readable; clicking the row or its chevron expands it (a newly created binding opens expanded and the page scrolls to it, however long the list). When expanded it shows a **Entradas** (inputs) group and a **Saídas** (outputs) group; each group lists its existing endpoints (device, channels, mode) with a trash action and an **add-endpoint** row. The add row uses **structured pickers — no free text**: a real **device ComboBox** populated from the enumerated audio interfaces, a **channel picker** derived from the chosen device's reported channel count (the same `ChannelOptionItem` model the Audio-interface section uses) — the shared `ChannelPicker` component: **one channel per row in a capped, vertically scrolling column**, never a horizontal strip, because interfaces with 30 inputs and 30 outputs are ordinary and a horizontal strip leaves everything past the window edge unreachable. Its header echoes the current selection and the device's total channel count, so neither is hidden by the scroll; mono draws radios (pick one), stereo/dual-mono draw checkboxes. The list has **no scroll area of its own**: Slint's `Flickable` intercepts a wheel gesture at `TouchPhase::Started` before its children, so the settings panel's scroll area owns the whole gesture and a nested list can only be moved by dragging its own scrollbar — every channel is laid out and the page scrolls, and a **mode** ComboBox (inputs: mono / dual_mono / stereo; outputs: mono / stereo). The Add button enables only once a device and at least one channel are chosen; the endpoint is auto-named ("In N" / "Out N"). The device lists are populated from the live hardware scan and refresh with the Audio-interface **refresh-devices** action. Deleting a binding that is still referenced by a chain is rejected with a message listing the referencing chains. A new project auto-creates a `default` binding from the system default input/output devices.
    - **Language** — UI locale override.
    - **Appearance** — the light/dark scheme: **System** (default, follows the OS), **Light** or **Dark**, as a segmented control. A pick repaints every open window at once (the compact view, block editor and chain editor included, while they stay open) and the windows opened later; `SetAppearance` sent over MCP repaints the same way. It is kept in `config.yaml` (`appearance`, ADR 0003) through `SettingsCommand::SetAppearance`.
    - **MIDI devices** — enable/disable each port, edit per-device alias.
    - **Integrations** — master switches for the MIDI/BLE-MIDI adapter and the MCP server (`config.yaml` `midi_enabled` / `mcp_enabled`, both default off). These gate whether the whole subsystem starts — distinct from the per-port MIDI-devices selection. Takes effect on next launch; `--midi` / `--mcp` override for a single run.
  - *Project* (persists to `project.yaml`, travels with the rig):
    - **Project metadata** — the name (editable) and the project file (read-only), two fields of one width stacked on the left, with **Save project** under them.
    - **MIDI mapping** — binding editor: click **+ Add**, press a control on your MIDI device (MIDI Learn), then pick a Command. Bindings are stored under `midi.bindings` in the `project.yaml`. The system-wide fallback (`midi-bindings.yaml`) is used when the open project has no `midi:` field.
- **Chain Editor** — name, instrument, I/O blocks. Input and Output blocks use an **I/O picker** (selects a binding by name) followed by an **endpoint picker** scoped to the chosen binding's input or output endpoints. The fullscreen "configure I/O" flow groups input and output blocks by binding, making the A-stream vs. B-stream grouping visible at a glance. Insert blocks use the same I/O picker, one binding for the whole loop.
- **Insert editor** — the editor of an **`Insert` block**, the external send/return loop. An insert carries exactly one thing: the **E/S** its loop runs through — the send goes out that binding's output, the return comes back on its input — so the window is that single picker plus the enable dot and the trash. Device, mode and channels belong to the E/S and are edited in Settings → I/O. Pressing OK with no E/S picked warns instead of saving an unbound loop, and an insert that stays unbound is bypassed by the engine (the chain plays straight through it) rather than silencing the chain.
- **Port editor** — the editor of a **mid-chain `Input`/`Output` port**, a port the user drops *between* effects (an aux send after the cab, a second source entering after the gate). A chain's own head/tail I/O is not a block — it comes from the E/S bindings — so this window edits only the two things a port carries: which **E/S** it points at and which **endpoint** of it, the same E/S pick the insert editor offers, plus an endpoint step. It has no model step: a port has no model and no parameters. Adding an `Input`/`Output` block opens it right after the block is created, and clicking a port already in the chain reopens it with its current E/S and endpoint filled in. The enable dot and the trash act on the port block itself. The chain row draws
one INPUT/OUTPUT meter pair per STREAM, so a mid port has its own bar and its own
clip indication (a rig with a mid `Input` and a mid `Output` shows four). Both selects receive a **fresh model on every open** — a `ComboBox` only recomputes the text it shows when its `model` or `current-index` changes, so rewriting rows in place left the box blank (`crates/adapter-gui/src/port_wiring.rs`).
- **Compact Chain View** — single-chain focused editor. The compact block chips and the chain-row header now display the **bound I/O name** (e.g. "Scarlett") instead of raw device strings. "Configure I/O" opens the binding-aware endpoint pickers described above.
- **Tuner** — one tuner per active **input port** under the current per-binding stream keys (`feature-dsp/pitch_yin.rs` + `engine/input_tap.rs` + `adapter-gui/tuner_session.rs`). With multiple input ports across bindings, each port gets its own tuner panel.
  - **One row per physical input, not per binding.** A row is a guitar: two bindings (or two chains) that read the same channel of the same interface hear the same string, so that channel gets ONE row, read from the first enabled input that carries it. The row is named after the interface and the input on its panel (`Quantum HD 8 · IN 1`); an interface the host no longer lists falls back to the binding input's name.
  - **In tune without words.** Rust decides it (`adapter-gui/tuner_tolerance.rs`, `IN_TUNE_CENTS` = ±3 ct) and publishes `in_tune` on the row and in `openrig://tuner`. Out of tune, the arrow on the side the note has to move toward lights amber (flat: the left ▶, sharp: the right ◀); in tune, both arrows, the needle, the centre tick and the note turn green, and the scale marks the in-tune zone.
  - **The dispatcher powers the analyzer**. POWER dispatches `SelectionCommand::SetTunerEnabled` and nothing else: the handler builds (or tears down) the analysis session through `RuntimeControl::set_tuner_running`, body in `adapter-gui/runtime_analyzers.rs`, so a MIDI footswitch bound to `toggle_tuner` and an MCP client light the same tuner the button does. The window only renders the rows the analyzer publishes, and `openrig://tuner` reads the very same session.
- **Spectrum** — one analyzer per active **output endpoint** under the per-binding stream keys, 63-band 1/6-octave (`feature-dsp/spectrum_fft.rs` + `engine/stream_tap.rs` + `adapter-gui/spectrum_session.rs`).
  - Each row is labelled `CHAIN  ·  <binding> IN <ch>  →  <binding> OUT <ch>  ·  L|R` — the binding names and 1-based channels the chain meters show (`spectrum_row_label.rs`, ui-rules §5), never the raw device id.
  - Powered the same way as the Tuner: `SelectionCommand::SetSpectrumEnabled` → `RuntimeControl::set_spectrum_running`, so `toggle_spectrum` on a footswitch and `openrig://spectrum` see the analyzer the window sees.
- **Metronome** — a **global** utility reached from the top bar, not a chain block: one metronome for the whole rig, independent of the active preset. Visually it follows the Tuner: the dark tool bar with the POWER pill, an amber LCD glass with the beat lamps, knob cells for every setting and a white TAP key (`adapter-gui/ui/pages/metronome_window.slint` + `ui/components/metronome_controls.slint`).
  - The LCD carries what a player reads mid-song: the tempo in large type, and one **beat lamp** per beat of the bar with the downbeat marked. The lamps read the generator's published **phase** on a 33 ms timer rather than a queue of events, so a slow UI frame can never lose or double a beat. During a count-in the lamps switch colour.
  - Controls: tempo 30–300 BPM (nudge buttons plus **TAP**, which averages the last four taps and discards any gap above 2 s), time signature, subdivision (off / eighths / triplets / sixteenths), timbre (click / wood / beep), click volume, count-in, and the **output**.
  - **Output = a project I/O output endpoint**, not a raw device: the picker lists the physical outputs of the project's I/O bindings by device and 1-based channels only ("Quantum HD 8 · Out 1/2", no binding name; a device the host no longer lists shows its id), so the click lands on the same device **and channels** the project is configured with. Endpoints of different bindings that route to the same device channels are one physical output and are listed once; a key saved for any of them still resolves to it. Picking one opens the metronome's own stream on that endpoint's device and routes the click only to that endpoint's channels. The picker is a plain in-panel list with clickable rows and a click-outside backdrop — **not** a `PopupWindow`, whose rows do not receive clicks in this app. The saved endpoint is used while it resolves; a renamed binding or a different machine falls back to the first output endpoint rather than going silent.
  - **The metronome never touches the guitar audio path.** It opens its **own** cpal output stream on the chosen endpoint's device and the backend sums it, exactly as the DI does — invariant 4 applied literally. No line was added to `process_output_f32`, `runtime_process_segment` or the output limiter, so a chain rebuild, a live edit or a chain failure cannot chop the click, and the click can never leak into a chain's buffers, its meters, or a recording taken off another output. The click plays even with **no chain enabled** — the dispatcher's `start_metronome` door creates the runtime the same way the DI's arm does, so a freshly opened project (every chain disabled) still sounds. See `docs/audio-config.md`.
  - The click is **synthesized** (`feature-dsp/metronome.rs`) — no samples, no decode, no resampling. Beat phase is an `f64` accumulator advanced per sample, so onsets land within one sample of the beat at any rate and under any callback size, with no drift.
  - Settings persist in **system** config (`config.yaml`), per ADR 0003, except the tempo, which is the project's and lives in `project.yaml`. `enabled` is deliberately **not** persisted — the app always opens with the click off.
  - **Closing the window only hides it — the click keeps playing; only POWER stops it.** A player can start the click, close the metronome, and keep working in the chains screen with the tempo still going; reopening shows POWER lit and the running beat (the open path reads the live enabled state, not a forced off).
  - The top-bar icon opens the metronome as its **own window** (`MetronomeWindow`) in windowed desktop mode, and **inline** over the chains page in fullscreen / touch mode — the same dual placement as the Tuner and Spectrum. Both host the same `MetronomePanel`, which reads its state from the `MetronomeBridge` global rather than bound properties: the panel has ~16 display values and a dozen callbacks, and threading those through `AppWindow → DesktopMain/TouchMain` would add hundreds of lines of forwarding to files already over the line-cap, so — like `DiPanel` — the state lives on one global the panel reads directly and the wiring sets once per window instance.
  - **The dispatcher owns the metronome**. Every control dispatches its `Command` and nothing else: the handler validates the value, stores it in `application::metronome_state`, writes `config.yaml` and applies it to the audio through `RuntimeControl` — so a tempo set from MCP, or POWER pressed on a MIDI footswitch, does exactly what the GUI's own knob does. The window (`adapter-gui/metronome_wiring.rs` + `metronome_controls_wiring.rs` + `metronome_events.rs`) only renders the dispatcher's snapshot; the knob-index ↔ command-key translation lives in `metronome_view.rs`, and the tap history lives in the dispatcher with the rest of the state.
  - The beat lamps read the click's position through `LiveSource::metronome` — a phase, not a queue of beat events — while a metronome surface is open. The same reading is served over MCP at `openrig://metronome`, so a client sees the tempo and the beat the click is actually on.
- **Backing tracks** — a **global** utility reached from the top bar (the track icon next to the drums): a player for practice tracks to jam over. It is not a chain block and has nothing to do with the DI: the DI feeds a dry guitar take *into* a chain, the player plays a finished mix *to an output*, past every chain (`adapter-gui/ui/pages/player_window.slint`).
  - The LCD shows the track name, `position / duration` in large type, and the A–B loop (or the pending loop start). Below it a **seek bar** (click to jump; the loop range is drawn on it), the transport as icons, like any deck — **stop** (back to 0:00), **play** and **pause**, and on the right the **A–B loop** button (first press marks A, second marks B, third turns the loop off; a second press closer than a fraction of a second to the first just re-marks A) — and three knobs: **level**, **speed** 0.5×–2× (pitch kept) and **pitch** ±12 semitones (tempo kept).
  - **Library:** tabs pick the part the player wants to practise — **Solo** (no lead, to solo over), **Rhythm** (no rhythm guitar), **Bass** (no bass) and **Acoustic** — and the list shows that tab's tracks: the ones bundled with the app (`assets/backing-tracks/<part>/`) first, then the user's own folder (`paths.backing_tracks_path`, default `backing-tracks/` under the OS data folder; editable in Settings → Paths). Only the user's own tracks carry a **trash** (first click arms it, second deletes the file — as on a DI take); the bundled ones have none. A track's part is the name of the subfolder it sits in (`solo`, `rhythm`, `bass`, `acoustic`, any case); files loose in the folder or in another subfolder land in an **Other** tab that appears only when there are any. Any wav, flac, mp3, ogg or m4a dropped there shows up the next time the panel opens. A click loads a track, a double click plays it. **Choose file…** plays a file from anywhere without copying it.
  - **Output = a project I/O output endpoint**, picked exactly like the metronome's (saved endpoint while it resolves, else the project's first output).
  - **Closing the window only hides it — the track keeps playing**; STOP or PAUSE end it. Same dual placement as the metronome: its own `PlayerWindow` in windowed desktop mode, inline over the chains page in fullscreen / touch mode, both hosting `PlayerPanel`, which reads the `PlayerBridge` global.
  - **The dispatcher owns the player.** Every control is a `Command` (`LoadPlayerTrack`, `SetPlayerPlaying`, `StopPlayer`, `SeekPlayer`, `SetPlayerVolume`, `SetPlayerSpeed`, `SetPlayerSemitones`, `SetPlayerLoop`, `ClearPlayerLoop`, `DeletePlayerTrack`, `SetPlayerOutput`), so MCP and MIDI drive it the way the GUI does; the state is served at `openrig://player`. Level and output persist in `config.yaml`; speed, pitch and loop belong to the track and reset when another one loads.
- **Drums** — the **global** play-along drum machine, reached from the top bar (the drum icon next to the metronome, lit while a groove plays). Same dual placement as the metronome: its own `DrumsWindow` in windowed desktop mode, inline over the chains page in fullscreen / touch mode; both host `DrumsPanel` (`adapter-gui/ui/pages/drums_window.slint`), which reads the `DrumsBridge` global. Top to bottom: POWER and the title, an amber LCD with one lamp per beat of the groove's bar, the tempo, the bar number and FILL while a fill plays; the KIT and GROOVE pickers (grooves grouped under one header per genre); the FILL footswitch (inert while stopped), the VOLUME knob (the tempo is the project's, set in the top bar); the OUTPUT picker. POWER is the one transport switch: on plays, off stops and closes the output, lit while the groove plays. Pickers are in-panel lists with a click-outside backdrop, not `PopupWindow`s. Every control dispatches a `DrumsCommand`; a frame poll moves the lamps and redraws when the state changes over MCP or MIDI. Details: `docs/drum-machine.md`.
- **Mixer** — a **global** utility reached from the top bar (the fader icon next to the metronome): one strip per **input** and per **output** endpoint of the system I/O bindings (`config.yaml`), in two tabs, INPUTS and OUTPUTS, each showing only its own strips. Top to bottom a strip shows the gain in dB, a vertical fader (-60 dB … +12 dB, unity at ~79% of the travel; double-click resets to 0 dB), one row of small buttons — **S** (solo), a speaker (mute; drawn crossed out and red while muted) and a reset arrow that puts the fader back to 0 dB — and at the bottom its label: the endpoint name from the I/O binding plus its 1-based interface channels (`IN 1`, `OUT 1,2`). The name is always one line, elided with "…" when too long, in its own reserved box that never overlaps the buttons; hovering the name shows it in full. SOLO silences the non-soloed strips of the same tab (several solos add up; the stored fader never moves); silenced strips read dim (`adapter-gui/ui/pages/mixer_window.slint` + `ui/components/mixer_strip.slint`).
  - **Every control is a `Command`** (`SetMixerFader`, `SetMixerMute`, `ToggleMixerMute`, `SetMixerSolo`, `ToggleMixerSolo`), so MCP tools and MIDI bindings do exactly what the fader does; the current values are served at `openrig://mixer`. The panel only reports a fader *position* — the position → dB law and the 0.1 dB rounding live in `adapter-gui/src/mixer_fader_law.rs`, and the side split and labels in `mixer_rows.rs`.
  - The gain is applied per endpoint through a lock-free atomic in the engine (`engine::mixer_gains`), with no buffer and no added latency; 0 dB is bit-identical to no mixer at all. Values persist in `config.yaml` under `mixer:` (only strips that differ from 0 dB / unmuted / unsoloed are written). A drag sends one `SetMixerFader` per tick, but each strip keeps at most one queued `config.yaml` write: later values replace the pending one and the write waits 150 ms for the drag to settle (`application::mixer_persist_coalesce`), so the file is never rewritten per pixel. While the fader is held, the cap follows the pointer by itself, and the redraws from the dispatcher update the strip rows in place (`adapter-gui/src/mixer_rows_sync.rs`). Replacing the model recreated the strip and dropped the pointer grab mid-drag, which is why faders felt stuck.
  - Same dual placement as the metronome: its own `MixerWindow` in windowed desktop mode, inline over the chains page in fullscreen / touch mode, both hosting `MixerPanel`, which reads the `MixerBridge` global. The window polls the dispatcher while open, so a change made over MCP or MIDI moves the fader on screen. The standalone window sizes its width to the strips of the open tab (120 px per strip + 32 px margins, 360 px minimum; `adapter-gui/src/mixer_window_size.rs`), when it opens and again when a tab switch changes the count. There is no screen-size query in the codebase, so the OS clamps a window wider than the screen, and past that the strip row scrolls sideways.
  - **Inline in the Compact Chain View:** the first section of the accordion below the block rows is a collapsible **MIXER** section (`ui/components/compact_chain_mixer.slint`). It always opens **collapsed**, showing only its header (a chevron, the faders icon and the title, `ui/components/section_toggle.slint`); a click on the header expands or collapses it. The expanded/collapsed state is never saved: every newly opened compact view starts collapsed. Expanded, it has up to four tabs — IN, OUT, DI and LOOPER; the **DI** tab shows only while the chain's DI loop plays and the **LOOPER** tab only while the chain has a looper, so a plain chain shows IN and OUT alone:
    - **IN / OUT** — OUT starts with the chain's **MASTER** fader (see below), then one **dual strip** per endpoint **this chain** plays through (`application::chain_mixer_strips`); the other endpoints of the machine never show there. A dual strip is one frame with one shared label at the bottom (binding name + channels) and two faders, each with its own dB readout, mute speaker and reset button: on the **left**, tinted and captioned **GLOBAL**, the endpoint's global strip — the same value the Mixer window moves (`Command::Mixer`, `mixer_strip_intents.rs`); on the **right**, the **chain's own fader** on that endpoint (`SetChainMixerFader` / `ToggleChainMixerMute`). The chain fader multiplies with the global one and never moves it or any other chain; it is project data (`Chain.mix`). There is no SOLO in the compact view (`ui/components/dual_mixer_strip.slint`).
    - **DI** — one fader: the chain's DI-loop gain (`SetChainDiFader`), applied to the DI before the chain.
    - **LOOPER** — one fader per looper of the chain: the looper's mix (`SetChainLooperParam` with `Mix`), capped at 0 dB (mix 1.0).
    - **MASTER** (first fader of the OUT tab) — the chain volume (the same value as the header's volume control, 0–200 %, so capped at +6 dB); the label shows the percentage.
    - DI, LOOPER and MASTER have no mute, only the reset button (back to 0 dB). Positions, labels and the dB ↔ percent / mix laws are computed in Rust (`chain_mixer_rows.rs`, `chain_level_law.rs`); gestures become intents in `chain_mixer_intents.rs` / `chain_fader_intent.rs`. A chain fader edit marks the project unsaved. The view polls every 100 ms and redraws when the global strips, the chain's bindings or the chain itself change (Mixer window, MCP, MIDI), updating rows in place so a held fader keeps its grab (`compact_mixer_wiring.rs`, `chain_mixer_rows_sync.rs`).
  - **From the chain list:** every chain card's header carries a **mixer** button (fader icon, left of the looper; offered on running and stopped chains alike — the faders are settings, not live levels). It opens **that chain's mixer** at the bottom of its card, below the IN/OUT meters (`ui/pages/chain_row_mixer.slint`); the card grows to hold it, with exactly the tabs and strips of the compact view's section (both host `ui/components/chain_mixer_tabs.slint`). One chain's mixer is open at a time: opening another chain's moves it there. Its GLOBAL halves are only the chain's own endpoints, drawn on the `ChainMixerPanel` global (`MixerBridge` keeps every endpoint for the Mixer window), and their gestures reach the same `Command::Mixer`. A second click on the same button closes it; it always reopens on IN. While open it polls every 100 ms like the compact view (`chain_mixer_panel_wiring.rs`, reading through `chain_mixer_source.rs`). The level meters button sits at the cluster's left end, so a stopped chain (no meters) leaves no gap. The title/preset area ends 8px before that cluster, and in a narrow window the chain title elides (down to 120px) instead of the row running under the buttons.
- **TONE3000** — the in-app TONE3000 browser, reached from the **T3K** logo button in the top bar (between the mixer and the settings gear; the logo keeps its own colours). **Browse** searches the public catalog with the user's own Secret Key (format / gear / sort filters, paged result cards with the A1/A2 choice and an Install action that turns into progress, INSTALLED or RETRY); without a key it says so and offers **Open settings**, which lands on Settings → Integrations, where the key card links to the TONE3000 page that creates keys. **Installed** lists the installed packages with a two-step uninstall. Every action is a `Command`; the state is `openrig://tone3000`. See [tone3000.md](tone3000.md) (`adapter-gui/ui/pages/tone3000_window.slint`).
- **Plugins** — the catalog of the user's own plugins, reached from the plugin button beside the T3K logo in the top bar. It lists every plugin that is not bundled with the app (plugins folder and TONE3000 installs), filtered by origin (all / plugins folder / TONE3000), by block type (searchable select) and by name. Each row shows the name, brand, block type, capture count and a TONE3000 mark, with icon actions: info (the plugin's info window), edit parameters, redo (**Update** on a TONE3000 plugin, which re-downloads a newer tone) and a two-step uninstall. **Create plugin** opens the editor empty. Every action is a `Command::PluginLibrary` (`adapter-gui/ui/pages/plugins_window.slint`).
- **Plugin editor** — one window for three uses: edit an installed plugin, create one, or name the parameters a TONE3000 install could not read (it opens by itself then; closing cancels that install). A grid with one row per capture (its source name, one cell per parameter, remove) and one column per parameter (name, kind List/Knob/Switch, remove, add). Edit mode adds a **Versions** search that restores a kept version and redo/update; create mode adds name, brand, block type, NAM/IR and **Add captures**. The info windows (floating and inline) show an **edit parameters** button for an editable plugin. See [plugin-editor/README.md](plugin-editor/README.md) (`adapter-gui/ui/pages/plugin_editor_window.slint`).

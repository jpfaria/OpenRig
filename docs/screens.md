# Telas principais

Pedalboard virtual: usuário monta cadeia de efeitos visualmente, ajusta parâmetros em tempo real, toca com áudio profissional.

- **Launcher** — criar/abrir projetos
- **Project Setup** — pede o nome ao criar novo projeto
- **Chains** — visualização da cadeia de blocos, drag/reorder. Tapping a chain row's header selects it (outlined) as the active chain — the one a MIDI footswitch bound to `toggle_active_chain_enabled` acts on (#591). A block whose model is not installed (an uninstalled NAM/IR/LV2 pack, or one unsupported on this platform) loads **disabled** and is shown dimmed with an amber tint, distinct from a manually-switched-off block; the chain keeps playing without it and its enable toggle stays inert until the pack is installed and the catalog reloads (#606).
  - **Per-stream meters** (#750) — the chain card footer renders one INPUT/OUTPUT peak-meter row per live input stream the chain runs. The rows are a **live surface**: they only appear while the chain is **enabled**. A disabled chain (including every chain on a freshly opened project) shows **no** meter rows. When enabled, the row count follows the chain's resolved input endpoints (e.g. two devices × two channels → four rows), and the meter timer fills the live dB values.
  - **Preset bank dropdown** (#659) — the per-chain preset selector opens a search-as-you-type finder: a search field filters the bank by name, and the list scrolls inside a height-capped popup so a large bank never runs past the screen (mirrors the block model picker). Each row keeps its original bank slot, so selecting a filtered entry switches to the right preset. The same dropdown is used in the Compact Chain View.
  - **Virtual DI loop** (#614) — each chain tile has a DI-loop icon button next to the per-chain volume knob. Clicking it expands a control row with: (1) a **select / dropdown** to choose the DI source, and (2) a **play / stop** toggle button. Available sources are the bundled CC0 dry-DI loops (shipped under `assets/di-loops/`) plus a **"Choose file…"** entry that opens a file picker for a user-supplied WAV. Pressing play replaces that chain's live device input with the looping DI buffer — the full block graph (amp, cab, pedals) processes it exactly as it would process the guitar signal. All other chains keep their real hardware input unaffected (per-stream isolation). The DI file must be a **dry DI** (clean guitar, no amp or effects); feeding already-processed audio will double-process the tone. A mono DI is broadcast to stereo (`Stereo([s, s])`); a stereo DI is used directly. If the chain has **several input sources**, the loop plays once — through the first source — and the other sources stay muted while it runs, so playback is never doubled (#699). The loop is **resampled to each output stream's own device rate** when it is armed (#749), so on a multi-rate rig (e.g. a 44.1 kHz interface and a 48 kHz interface at once) every output plays at correct speed/pitch — not just the one matching a single global rate. Changing the device rate while a loop is playing re-arms it at the new rate, so it never drags into slow motion (#669). The loop choice and on/off state are **ephemeral (runtime-only)**: they are never written to the project (`.openrig`) — consistent with ADR 0003. Reopening or reloading the project returns every chain to its live hardware input. **Isolated streamed DI (#771):** the DI loop never touches the guitar's stream. Arming builds a fresh routed copy of the chain's block graph on a worker thread and **streams** the loop through it into a lock-free ring the chosen output's callback drains — playback starts within milliseconds regardless of loop length, the worker only produces what the output consumed (ring backpressure → the output clock IS the DI clock, no drift), and no DSP runs in the callback. The sound is mixed into the **chosen output only**; the guitar's live signal, meters, and other outputs are untouched (invariant #4). The DI runtime is a snapshot of the chain: block edits made while the loop plays apply on the **next** play. The DI panel has a second select listing the chain's **already-bound output endpoints**; picking one dispatches `SetChainDiLoopOutput` and a playing loop re-renders onto the new output. The choice persists per-chain in `project.openrig` (`Chain.di_output`, ADR 0003; absent → the chain's main output). The **DI meter row** (compact window) shows the DI stream's **own** in/out levels, read from the playback's peaks — not a mirror of the chain meters.
  - **Looper** (#323) — each chain tile has a loop icon next to the DI fone. Clicking it opens the **looper panel** at the window root (an inline panel, never a `PopupWindow`, so every control is reachable — the #749/#761 lesson): one **stacked row per looper**, plus a **+ Add** button, and an empty state explaining what a looper does. A chain can hold up to **8** loopers and they are fully independent — any number can record or play at the same time. Each looper is **single-take** (one recording, no overdub layers): to stack parts you add another looper, not layers on one. REC starts the recording and a second REC closes it; there is no undo/redo. Each row carries a 40 px transport (record · play/stop · clear), the state as **colour AND label** (grey empty, red recording, blue playing, light grey stopped), a position bar with `0:03 / 0:08` at the stream's real rate, a gear that opens the row's **parameter drawer** (record-from **input** and play-to **output** selects, level, decay, speed ½×/1×/2×, reverse), and an × that removes the looper. Each looper picks **which input it records from** (so on a multi-input rig REC captures the input you actually play, not always the first) and **which output it plays to**. A looper records the chosen input's **dry signal**; playback runs on its own **isolated stream** — a routed copy of the chain into the chosen output (the same isolated pipeline as the DI loop, #771), so input and output are fully independent and the loop never mixes into the record chain (invariant #4). **Tone independence (phase 2):** because the loop records **dry**, it carries a reference to **which preset renders it** — so you can record on preset A, switch the chain to B to solo live, and the loop keeps A's tone. On a **fresh** RECORD the loop is linked to the chain's currently-active preset; the drawer's **preset picker** (a `Preset ▸ <name>` button that opens a root-level modal listing the chain's bank, plus a *follow the chain* entry that clears the link) reassigns it at any time. Editing the linked preset's blocks re-renders the loop through the new tone on the next play. The playback stream is built from the **linked** preset's effects — a routed copy of the chain with its processing swapped, same I/O and stream identity so isolation is untouched (invariant #4). The link is a `Command` (`SetChainLooperPreset`) so MCP/gRPC reach it too, and it persists on the chain (`LooperConfig.preset`; rig projects store it inside the `RigInput`'s loopers). **REC is offered only while the chain is running (enabled)** — recording captures the live input through the chain's runtime, which exists only then, so on a stopped chain the REC button is disabled (dimmed) rather than a dead press. Play/clear act on already-recorded material and stay available regardless. **A loop's state (the recorded audio and its transport) lives in the controller, not inside the chain's audio runtime** — so stop/clear/remove take effect immediately and a loop survives an enable toggle or a project reopen instead of being lost when the runtime rebuilds. Level and reverse shape the playback; speed is a follow-up. Recording is capped at **60 s**. Loops are per chain and per runtime: nothing is shared with another chain (invariant #4). A **footswitch** drives the first looper of the active chain through the MIDI slots `looper_record`, `looper_play_stop` and `looper_clear` (see `docs/midi-profiles.md`). Recorded audio is saved with the project as a wav under `<project>.loops/` and comes back **stopped** (never auto-playing) when the project is reopened, resampled if the interface now runs at a different rate; the parameters travel inside the `.openrig`.
- **Block Editor** — edita parâmetros de um bloco. The header's model select/search picker is shown only for catalog-backed block types; the generic NAM (`nam`) and IR (`ir`) file-loader blocks have no catalog model to choose, so their header shows the loaded model name as a static label instead of the picker (#608). The editor window sizes itself to its content so every parameter is visible without scrolling — the panel (knob-grid) editor grows vertically as knobs wrap into rows, and the form editor grows with its parameter count (it was previously locked to a fixed 820px, hiding the lower params behind an internal scroll) (#622). **Adding a block opens the same editor (#815):** outside the inline fullscreen/touch mode, picking a block type no longer opens a separate window — it opens this very editor in **add-mode**, so the parameter tabs of #780/#786 are there while you are still choosing the model, exactly as when editing an existing block. The two modes differ only in commitment: in add-mode the confirm button reads *add*, the delete affordance is hidden (there is nothing to delete yet), and **nothing is written until you confirm** (no auto-persist as you turn a knob, no live stream refresh), so abandoning the window leaves the chain untouched; editing an existing block keeps persisting each change as before.
- **Compact Chain View** — single-chain focused editor: power switches, quick model swap, preset/scene picker, volume, configure I/O, and a **measure-latency** button whose result renders as a badge **inside this view** (next to the sonar button), not on the chains list behind it (#613). Its block-type picker uses the same tiles as the Chains screen, so the icons match. Chain reorder (move up/down) is intentionally absent here — it lives only on the Chains list, which is the multi-chain view (#613). **Rows size themselves to their parameters (#787):** a block's parameter strip wraps into as many lines as it needs and the row grows to fit them, instead of clipping the params away at a fixed height; a block whose parameters carry 2+ groups (a VST3 plugin's manifest groups, or the dynamic grouping of #780) gets a **tab bar** on top of its strip and shows one group at a time. A block with a single group and one line of knobs looks exactly as it did before. Which tab a block shows is view state — it is never written to the project — and it survives the model rebuild that every parameter edit triggers. The drag-to-reorder drop indicator follows the real row boundaries, since rows no longer share a fixed height.
- **Settings** — unified configuration screen, reached from the top bar. Two scope headers:
  - *System* (persists to `config.yaml`, stays on the machine when you move the `.openrig`):
    - **Audio interface** — input/output device, sample rate, buffer size, bit depth. The first-run audio wizard and device-change flow also create or update the `default` I/O binding so new chains always have a binding to reference.
    - **I/O bindings** (#716) — list, create, edit, and delete named I/O bindings. Each binding is a **collapsible accordion**: collapsed by default showing only its name plus In (green) / Out (orange) endpoint counts, so a list of several E/S stays readable; clicking the row or its chevron expands it (a newly created binding opens expanded). When expanded it shows a **Entradas** (inputs) group and a **Saídas** (outputs) group; each group lists its existing endpoints (device, channels, mode) with a trash action and an **add-endpoint** row. The add row uses **structured pickers — no free text**: a real **device ComboBox** populated from the enumerated audio interfaces, **channel checkboxes** derived from the chosen device's reported channel count (the same `ChannelOptionItem` model the Audio-interface section uses), and a **mode** ComboBox (inputs: mono / dual_mono / stereo; outputs: mono / stereo). The Add button enables only once a device and at least one channel are chosen; the endpoint is auto-named ("In N" / "Out N"). The device lists are populated from the live hardware scan and refresh with the Audio-interface **refresh-devices** action. Deleting a binding that is still referenced by a chain is rejected with a message listing the referencing chains. A new project auto-creates a `default` binding from the system default input/output devices.
    - **Language** — UI locale override.
    - **MIDI devices** — enable/disable each port, edit per-device alias.
    - **Integrations** (#712) — master switches for the MIDI/BLE-MIDI adapter and the MCP server (`config.yaml` `midi_enabled` / `mcp_enabled`, both default off). These gate whether the whole subsystem starts — distinct from the per-port MIDI-devices selection. Takes effect on next launch; `--midi` / `--mcp` override for a single run.
  - *Project* (persists to `.openrig`, travels with the rig):
    - **Project metadata** — name and other project-level fields.
    - **MIDI mapping** — binding editor: click **+ Add**, press a control on your MIDI device (MIDI Learn), then pick a Command. Bindings are stored under `midi.bindings` in the `.openrig`. The system-wide fallback (`midi-bindings.yaml`) is used when the open project has no `midi:` field.
- **Chain Editor** — name, instrument, I/O blocks. Input and Output blocks use an **I/O picker** (selects a binding by name) followed by an **endpoint picker** scoped to the chosen binding's input or output endpoints. The fullscreen "configure I/O" flow groups input and output blocks by binding, making the A-stream vs. B-stream grouping visible at a glance (closes #257). Insert blocks keep their raw send/return endpoint fields and are not migrated to the registry.
- **Compact Chain View** — single-chain focused editor. The compact block chips and the chain-row header now display the **bound I/O name** (e.g. "Scarlett") instead of raw device strings. "Configure I/O" opens the binding-aware endpoint pickers described above.
- **Tuner** — one tuner per active **input port** under the current per-binding stream keys (`feature-dsp/pitch_yin.rs` + `engine/input_tap.rs` + `adapter-gui/tuner_session.rs`). With multiple input ports across bindings, each port gets its own tuner panel.
- **Spectrum** — one analyzer per active **output endpoint** under the per-binding stream keys, 63-band 1/6-octave (`feature-dsp/spectrum_fft.rs` + `engine/output_tap.rs` + `adapter-gui/spectrum_session.rs`).
- **Metronome** (#14) — a **global** utility reached from the top bar, not a chain block: one metronome for the whole rig, independent of the active preset. Visually it follows the Tuner: power footswitch, amber LCD, and the pedal vocabulary of rotary knobs (`adapter-gui/ui/pages/metronome_window.slint` + `ui/components/metronome_controls.slint`).
  - The LCD carries what a player reads mid-song: the tempo in large type, and one **beat lamp** per beat of the bar with the downbeat marked. The lamps read the generator's published **phase** on a 33 ms timer rather than a queue of events, so a slow UI frame can never lose or double a beat. During a count-in the lamps switch colour.
  - Controls: tempo 30–300 BPM (nudge buttons plus **TAP**, which averages the last four taps and discards any gap above 2 s), time signature, subdivision (off / eighths / triplets / sixteenths), timbre (click / wood / beep), click volume, count-in, and the **output**.
  - **Output = a project I/O output endpoint** (#14), not a raw device: the picker lists the output endpoints of the project's I/O bindings ("Binding · Endpoint"), so the click lands on the same device **and channels** the project is configured with. Picking one opens the metronome's own stream on that endpoint's device and routes the click only to that endpoint's channels. The picker is a plain in-panel list with clickable rows and a click-outside backdrop — **not** a `PopupWindow`, whose rows do not receive clicks in this app (#749/#761). The saved endpoint is used while it resolves; a renamed binding or a different machine falls back to the first output endpoint rather than going silent.
  - **The metronome never touches the guitar audio path.** It opens its **own** cpal output stream on the chosen endpoint's device and the backend sums it, exactly as the DI does since #808 — invariant #4 applied literally. No line was added to `process_output_f32`, `runtime_process_segment` or the output limiter, so a chain rebuild, a live edit or a chain failure cannot chop the click, and the click can never leak into a chain's buffers, its meters, or a recording taken off another output. The click plays even with **no chain enabled** — `start_click` creates the runtime the same way the DI does (#808), so a freshly opened project (every chain disabled) still sounds. See `docs/audio-config.md`.
  - The click is **synthesized** (`feature-dsp/metronome.rs`) — no samples, no decode, no resampling. Beat phase is an `f64` accumulator advanced per sample, so onsets land within one sample of the beat at any rate and under any callback size, with no drift.
  - Settings persist in **system** config (`config.yaml`), per ADR 0003: a practice tempo does not travel with the `.openrig`. `enabled` is deliberately **not** persisted — the app always opens with the click off. Per-preset BPM and global tap tempo remain #322.
  - **Closing the window only hides it — the click keeps playing; only POWER stops it.** A player can start the click, close the metronome, and keep working in the chains screen with the tempo still going; reopening shows POWER lit and the running beat (the open path reads the live enabled state, not a forced off).
  - The top-bar icon opens the metronome as its **own window** (`MetronomeWindow`) in windowed desktop mode, and **inline** over the chains page in fullscreen / touch mode — the same dual placement as the Tuner and Spectrum. Both host the same `MetronomePanel`, which reads its state from the `MetronomeBridge` global rather than bound properties: the panel has ~16 display values and a dozen callbacks, and threading those through `AppWindow → DesktopMain/TouchMain` would add hundreds of lines of forwarding to files already over the line-cap, so — like `DiPanel` (#749) — the state lives on one global the panel reads directly and the wiring sets once per window instance.
  - Every control dispatches its `Command` and reacts to the `Event` that comes back (`adapter-gui/metronome_wiring.rs` + `metronome_controls_wiring.rs` + `metronome_events.rs`); that single door is what writes the session, the window, `config.yaml` and the audio runtime, so a tempo set from MCP or a MIDI footswitch lands exactly where the GUI's own knob does. The tap history and the knob-index ↔ command-key translation live in `metronome_session.rs`.
